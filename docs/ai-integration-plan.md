# AI integration plan

## Current state, stated plainly

**No AI provider is configured, and none is called.** Every AI-assisted feature in
this prototype runs through `PrototypeAIProvider`, which restructures content the
professor already entered. It reports `isSimulated: true`, and the interface renders
that as *"Sample output — no AI provider is configured"* wherever the output
appears, together with a note describing exactly what it was derived from.

The application does not claim a model is running. That is the whole point of the
provenance layer.

## The interface

`src/lib/ai/types.ts`:

```ts
interface AIProvider {
  readonly id: string
  readonly label: string
  readonly isSimulated: boolean

  generateSummary(input: LectureContext): Promise<AIResult<SummaryPayload>>
  extractConcepts(input: LectureContext): Promise<AIResult<ExtractedConcept[]>>
  generateQuestions(input: LectureContext, count: number): Promise<AIResult<GeneratedQuestion[]>>
  generateFlashcards(input: LectureContext, count: number): Promise<AIResult<Flashcard[]>>
  generateStudyGuide(input: StudyGuideInput): Promise<AIResult<StudyGuidePayload>>
  extractSyllabus(rawText: string, courseTitle: string): Promise<AIResult<SyllabusExtraction>>
  analyzeReadiness(input: ReadinessNarrativeInput): Promise<AIResult<ReadinessNarrative>>
  recommendSupport(input: ReadinessNarrativeInput & { pathwayTitles: string[] }): Promise<AIResult<SupportNarrative>>
  prepareOfficeHours(input: { studentName: string; topics: string[]; reasons: string[] }): Promise<AIResult<OfficeHoursBrief>>
}
```

Every method returns `AIResult<T>`:

```ts
type AIResult<T> = { data: T; provenance: Provenance }

type Provenance = {
  providerId: string
  providerLabel: string
  isSimulated: boolean     // false only when a real model produced this
  model: string | null
  generatedAt: string
  sourceNote: string       // what it was derived from, shown to the user
}
```

Nothing in the application calls a model directly, and no feature code branches on
which provider is active. Provenance travels with the payload rather than being
reconstructed at render time, so output stored months ago still labels itself
accurately after the provider changes.

## What the prototype provider actually does

Deliberately not clever, and honest about it.

| Method | Behaviour |
| --- | --- |
| `generateSummary` | Extracts sentences from segment bodies; lists segment headings and key terms as points. |
| `extractConcepts` | Returns professor-entered concepts, plus up to four segment headings not already covered. Attaches a perspective note for terms on a contested-terms list (justification, sola fide, real presence, predestination, sacrament, law and gospel). |
| `generateQuestions` | Templates one question per key term and per section. Marked as placeholder drafts, and says so in the explanation text where no definition exists. |
| `generateFlashcards` | Key terms, scripture references and section headings as front/back pairs. |
| `generateStudyGuide` | Regroups objectives, key terms and (for a student) their own questions and exam-review notes. Adds no new content. |
| `extractSyllabus` | **Genuine rule-based parsing.** Matches common headings ("Learning Objectives", "Weekly Schedule", "Readings", "Assignments", "Exams", "Grading"), `Week N —` patterns, bullets and inline dates. Reports honestly when nothing is recognised, including the fact that it does not understand prose. |
| `analyzeReadiness` | Restates the readiness engine's recorded signals. Invents nothing. |
| `recommendSupport` | Narrates the deterministic recommender's ordering. |
| `prepareOfficeHours` | Assembles a two-sided brief from the topics the student selected and the recorded signals. **Never reads private notes.** |

Deterministic: the same input always produces the same output. That is what makes
the workflow demonstrable without a model, and what makes the verification suite
able to assert on it.

## Adding a real provider

1. Implement `AIProvider` in `src/lib/ai/<provider>-provider.ts`. Set
   `isSimulated = false` and populate `model` in the provenance.
2. Add one branch to the switch in `getAIProvider()` (`src/lib/ai/index.ts`).
3. Set `AI_PROVIDER=<name>` and whatever credentials that provider needs, via
   environment variables only.

No feature code changes. `AIProvenance` will begin rendering *"Generated by
&lt;label&gt; (&lt;model&gt;)"* instead of the sample-output notice automatically.

`AI_PROVIDER` set to an unimplemented value logs a warning and falls back to the
deterministic provider. It does not throw at request time, and it does not silently
pretend — `/about` shows the requested value alongside a note that it is not
implemented.

## Rules any real provider must follow

These are product requirements, not implementation notes.

**Prioritise professor-approved content.** Every prompt should be grounded in the
course's own published material — segments, notes, transcript, professor-entered
definitions and objectives — and should say so in its `sourceNote`. The
deterministic provider models this by construction: it literally cannot produce
anything not already in the course.

**Never present theological interpretation as settled where it is contested.** The
prototype maintains a contested-terms list and attaches a note explaining that
traditions differ. A real provider must do at least as much, and should distinguish
in its output between:

- the source material,
- the professor's own interpretation,
- a historical position,
- a denominational position,
- the model's own explanation.

The seeded course data models this: the concept `Justification` carries the note
*"Lutheran, Reformed, Catholic and more recent readings of Paul differ
substantially here. This course teaches Luther's position as Luther held it, then
compares it with others — it does not treat any one account as settled."*

**Label everything.** No AI output reaches a screen without `AIProvenance` beside
it. Non-negotiable.

**Require human review for course-wide material.** Anything that would be seen by
a class stays a draft until a professor approves it. `NeedsReviewFrame` renders
this visibly: *"Draft — not visible to students until a professor approves it."*
Enforced in data by `ai_artifacts.approved`.

**Never auto-import.** Drafted assessment questions are shown for the professor to
copy and edit. Deliberately not one-click importable — a question that lands in a
student's assessment without a human reading it is exactly the failure mode this
guard exists to prevent.

**Never read private student notes.** Support briefs and readiness narratives are
built from recorded signals and student-selected topics. Repository-level
enforcement (`listSharedNotes`) is the backstop, but a provider integration must
also not be handed private note text in a prompt.

**Do not score theological writing.** `HUMAN_GRADED_ASSESSMENT_TYPES` names essays,
reflection papers and oral examinations. Short-answer responses store `is_correct`
as NULL permanently. A provider may help a professor read; it may not produce a
judgement presented as authoritative.

## Where AI is wired in now

| Surface | Method | Review gate |
| --- | --- | --- |
| Professor → Syllabus | `extractSyllabus` | Row-level approval before publishing |
| Professor → Assessments | `generateQuestions` | Drafts only; manual copy-edit |
| Professor → Assessments | `generateStudyGuide` | `NeedsReviewFrame` |
| Student → Notes | `generateStudyGuide` | Labelled; student-scoped |
| Student → Notes | `generateFlashcards` | Labelled; student-scoped |
| Student → Support request | `prepareOfficeHours` | Shown to both sides before use |

`generateSummary`, `extractConcepts`, `analyzeReadiness` and `recommendSupport` are
implemented and tested but not yet surfaced in the UI, because the deterministic
versions add little over what the readiness and support engines already render
directly. They are the natural first places a real provider would earn its keep.

## Sequencing for a real integration

**First — syllabus extraction.** Highest value, lowest risk. The review gate
already exists, the failure mode is visible (a wrong row is obvious), and the
rule-based parser is genuinely weak at prose.

**Second — lecture transcription and summarisation.** Removes real professor
effort. Needs a transcription provider, and needs an explicit accuracy caveat on
generated captions.

**Third — question drafting.** Useful, but the review burden is real. Keep the
no-auto-import rule.

**Fourth — student study material.** Study guides and flashcards from a student's
own notes. Requires care that the student's private notes stay within their own
session and are never used to generate anything another person sees.

**Not recommended** without substantial institutional review: automated readiness
narratives that go beyond restating recorded signals, and anything that scores
written theological work.

## Cost and privacy

Neither is addressed in this prototype, and both block production.

Sending course material or student activity to a third-party model provider is a
disclosure of education records. That requires a data-processing agreement, a
review of the provider's retention and training policies, a decision on whether
student-authored text may ever leave the institution, and — probably — student
notice. `privacy-and-student-data-considerations.md` treats this as a gating item,
not a detail.

## Environment variables

```
AI_PROVIDER=prototype      # or unset. Any other value warns and falls back.
```

No API keys are read anywhere in the codebase today. Any provider must read its
credentials from environment variables and must not log them.
